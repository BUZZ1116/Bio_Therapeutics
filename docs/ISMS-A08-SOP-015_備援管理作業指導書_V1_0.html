1. 作業目的

本作業指導書規範組織備援管理之需求識別、風險分級、架構設計、建置、監控、測試、切換、回切、維護、例外、供應商管理與稽核要求，確保關鍵資訊系統及支援性ICT服務在故障、資安事件、自然災害、雲端區域中斷、供應商中斷、資料損毀、人為錯誤或容量耗盡時，能符合業務持續與資訊安全要求，維持可用性、完整性與可恢復性。

本文件旨在將備援管理與BCMS、ICT備妥性、備份還原、事件管理、變更管理、弱點管理、供應商管理、雲端韌性、AI/MLOps治理及日誌監控整合，建立可測試、可追溯、可驗證且可持續改善之企業級備援能力。

2. 作業原則

  • 備援設計應以業務影響分析、風險評估、RTO、RPO、MTPD、SLA、SLO、資料分類與法規/合約要求為基礎。
  • 備援不等於備份；備援著重服務持續與快速切換，備份著重資料保護與可復原，兩者應互相驗證。
  • 關鍵服務應避免單點失效，包含人員、系統、資料、網路、雲端區域、身份服務、金鑰、DNS、監控、供應商及流程。
  • 備援架構應具備安全等級一致性，備援環境不得成為弱化控制、未修補、未監控或權限過寬之風險來源。
  • 備援切換與回切應事前定義條件、權責、程序、資料一致性檢查、風險接受、通報與事後檢討要求。
  • 未經測試之備援能力不得視為有效；所有Critical/High系統應依風險定期執行演練、測試或桌上推演。

3. 名詞與定義

名詞 定義
備援 為降低單點失效並維持服務可用性而設置之替代系統、資源、站點、網路、資料、流程或供應能力。
高可用性（HA） 透過叢集、負載平衡、自動故障切換、容錯設計等方式降低服務中斷時間之能力。
災難復原（DR） 當主要環境不可用時，在替代站點或環境恢復服務與資料之能力。
RTO Recovery Time Objective，復原時間目標，服務需於多長時間內恢復至可接受狀態。
RPO Recovery Point Objective，復原點目標，可接受之最大資料遺失時間。
MTPD Maximum Tolerable Period of Disruption，最大可容忍中斷時間。
Failover 主環境故障時切換至備援環境、節點或服務之活動。
Failback 主要環境恢復後，由備援環境回切至主要環境之活動。
Active-Active 主要與備援資源同時承載服務或流量之架構。
Active-Passive 主要資源承載服務，備援資源待命，於故障時啟用之架構。
冷備援 / 溫備援 / 熱備援 依備援資源啟用速度、資料同步狀態與成本不同所形成之備援等級。
Split-brain 叢集或複寫環境中多個節點同時認為自身為主節點，可能造成資料不一致之狀態。

5. 備援等級與適用標準

備援等級 適用情境 典型架構 最低要求
Level 0 無正式備援 低重要性、可手動重建或短期中斷可接受之系統。 文件化重建、手動替代流程。 需Business Owner接受，仍應有基本備份。
Level 1 冷備援 中低重要性系統，可接受較長復原時間。 預備資源、備份還原、手動部署。 具重建文件、備份與定期還原測試。
Level 2 溫備援 中高重要性系統，需於合理時間恢復。 預置環境、定期資料同步、手動切換。 定期同步驗證、切換程序與測試。
Level 3 熱備援 高重要性系統，需短時間切換。 即時或近即時複寫、待命環境、可快速切換。 持續監控、自動化或半自動切換。
Level 4 高可用 / Active-Active 關鍵服務或SLA嚴格服務。 多節點、多區域、負載平衡、自動故障切換。 自動偵測、容量冗餘、資料一致性控制。
Level 5 多區域 / 多供應商韌性 極關鍵或受法規/客戶要求之服務。 跨區域、跨雲、替代供應商或離線應變。 正式演練、管理層核准、供應商證據與持續監控。

6. 備援管理流程

階段 作業要求 責任角色 輸出證據
1. 業務影響與需求識別 識別服務重要性、MTPD、RTO、RPO、SLA、法規、合約與資料分類。 Business Owner / BCMS Owner BIA與ICT備妥性評估。
2. 風險評估 評估單點失效、資料損毀、區域中斷、供應商中斷、資安事件與人員依賴。 Risk Owner / CISO 風險評估紀錄。
3. 備援策略選擇 選擇冷/溫/熱/Active-Active/多區域/替代流程等策略。 Service Owner / Infrastructure 備援策略與設計。
4. 安全架構審查 確認備援環境之IAM、加密、網段、日誌、弱點、金鑰、資料保護與監控。 Security Architecture / CISO 安全審查紀錄。
5. 建置與設定 依核准設計建置備援資源、複寫、網路、DNS、監控、切換腳本與權限。 IT Operations / Cloud Owner 建置與變更紀錄。
6. 資料與服務驗證 驗證資料一致性、複寫延遲、服務健康、容量、告警與切換前條件。 System Owner / Database Owner 驗證報告。
7. 測試與演練 依等級執行桌上推演、技術切換、還原測試、DR演練或供應商演練。 BCMS / Availability Owner 演練與測試紀錄。
8. 上線監控 持續監控備援健康、容量、同步狀態、延遲、錯誤、告警與SLA。 SOC / IT Operations 監控報告。
9. 變更與維護 任何主/備架構、RTO/RPO、網路、DNS、IAM、KMS、資料複寫變更均需管制。 Change Owner 變更紀錄。
10. 檢討改善 依測試、事件、稽核與KPI/KRI結果改善備援能力。 ISMS代表 / Service Owner CAPA與管理審查紀錄。

7. 備援需求與設計要求

設計領域 最低要求 高風險加強要求
服務範圍 明確定義納入備援之應用、資料庫、API、網路、身份、金鑰、監控與供應商。 建立端到端服務依賴圖與資料流。
RTO/RPO 每項關鍵服務需定義RTO/RPO並取得Business Owner核准。 RTO/RPO需定期測試證明可達成。
容量冗餘 備援環境容量需足以承載最低可接受業務負載。 Active-Active需設計N+1或等效容量。
資料一致性 定義同步方式、延遲、衝突處理、完整性檢查與Split-brain防護。 關鍵資料需自動完整性驗證與不可變紀錄。
身份與存取 備援環境IAM、PAM、MFA、服務帳號與權限需與正式環境一致或等效。 切換時不得使用共享帳號或臨時弱密碼。
加密與金鑰 備援資料、複寫、備份、金鑰與Secrets需受同等保護。 KMS/HSM需跨區可用且權限受控。
網路與DNS 切換需考量DNS TTL、路由、Load Balancer、VPN、WAF、API Gateway與防火牆規則。 高關鍵服務需預先測試DNS/Route切換。
監控與日誌 備援環境需納入監控、日誌、SIEM、告警與事件處理。 切換後告警不得中斷或失真。
安全基準 備援環境需符合安全組態、弱點修補、EDR、DLP與存取控制要求。 不得因備援環境降低安全控制。
回切能力 需定義主環境恢復後之資料同步、驗證、回切、通報與風險評估。 回切前需管理層或指定Owner核准。

10. 切換與回切管理要求

技術執行 依Runbook進行DNS、路由、LB、WAF、API、DB、Queue、KMS、IAM與監控切換。 依Runbook回切並逐項驗證。

業務驗收 業務Owner確認最低服務能力、關鍵功能與資料可用性。 業務Owner確認服務恢復至正常狀態。
事後檢討 記錄切換原因、時間、影響、問題、資料差異與改善。 回切後完成事件檢討與CAPA。
